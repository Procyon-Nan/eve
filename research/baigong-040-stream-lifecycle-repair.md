## R02：取消后不再创建读取器

修改 `packages/eve/scripts/vendor-compiled/@workflow/core.mjs`，接入独立的流生命周期补丁文件。目标为依赖 `dist/serialization.js` 的 `createReconnectingFramedStream`，并覆盖同文件字节流读取器的异步连接清理。

实现规则：

1. 每个读取流只有一份终止状态。`cancel()` 开始时同步置为终止，随后清理；重复调用复用同一次清理。
2. 取下当前 reader 后取消它，最后释放锁。不能先等待正在阻塞的 `read()` 结束才取消，否则会互相等待。
3. 连接、读取、EOF 元数据查询、重连的每次 `await` 返回后检查终止状态。已终止则不入队、不重连、不操作已关闭的 controller。
4. `streams.get()` 在取消后才返回时，立即取消并释放这个迟到 reader。取消的完成覆盖已发起连接的清理；不增加超时来假装清理成功。World 的 get 没有取消参数，尚未返回的单次 I/O 只能等待其结算，不能声称已中止它。
5. 正常 EOF、不可继续的错误也释放 reader。保留真实断流重连、原有重试上限、完整帧游标及负索引行为；半帧不能推进恢复游标。

**审查重点：** 取消产生的 `done` 不进入重连；迟到 reader 有唯一清理者；释放锁不会遗留读请求。会话 `waiting` 合法，没有 EOF 不等于应该关闭持久流。

2026-10-27 实施记录：新增 `core-stream-lifecycle.mjs` 并接入 vendoring。帧流和字节流共用一个内部 reader 所有者，统一处理连接、取消及释放；不增加公共接口。静态审查覆盖等待读取、迟到连接、重连清理、正常 EOF、错误和半帧游标路径，未发现阻止提交的问题。补丁应用、构建、运行时资源归零及业务行为留待 R08 验收，不以本次静态审查代替。

## R03：文件读取失败不能跳过事件

修改 `packages/eve/scripts/vendor-compiled/@workflow/world-local.mjs`，接入针对依赖 `dist/streamer.js` 的补丁。

- 初始化、取消、EOF、读取异常共用幂等清理，移除两个事件监听器并清除定时器。每次异步读取返回后、启动定时器前检查终止状态。
- 保留 100ms 文件轮询及禁止重叠轮询的约束。不开新轮询服务，不改变写入格式。
- 将“读取中”“暂存事件”“已交付”区分开。只有成功交付后才标记已交付；不能在 `readBuffer()` 前占用已交付标记。
- 同进程事件在磁盘读取期间进入现有缓冲区；初始化和轮询的磁盘读取共用这一约束。交付时按块顺序合并并再次去重，避免磁盘读取与事件回调各发一次。关闭事件等已有块排空后处理。
- 读块失败使当前 reader 报错并清理，不跳过坏块继续交付后面的块。上层若按原策略重连，从尚未成功交付的游标恢复。`EIO`、`EACCES` 等不能因带有 `code` 就被吞掉。
- 保留“尚未创建的空流目录”这一正常情况；已枚举出的块读取失败与空目录不同，必须报错。取消之后迟到的错误只完成清理，不二次关闭 controller。

**审查重点：** `first` 读取失败后不能只返回 `second` 再正常 EOF；初始化和轮询失败都没有残留监听器；事件与磁盘交错仍保持顺序、去重和游标语义。

2026-10-27 实施记录：新增 `world-local-stream-lifecycle.mjs` 并接入 vendoring。初始化与轮询共用读块和交付逻辑，读块成功后才记已交付；磁盘读取期间的同进程事件缓冲并在交付时去重。初始化及轮询异常终止当前 reader，清除监听器和定时器。静态审查覆盖取消与异步读取交错、错误后不推进交付、重复事件、负索引及 EOF 路径，未发现阻止提交的问题。运行时和真实文件验收留待 R08。

## R05：回执只保留一条等待链

修改 `packages/eve/src/runtime/host-runtime/acceptance.ts`。

- 删除 `Promise.race(getRun(...).returnValue, timeout)` 这条不能停止底层轮询的等待。
- `recordHostRuntimeAcceptance()` 先读现有持久状态；已有相同终态则返回，冲突终态仍报不确定。需要提交时继续使用原来的 `resumeHook()`。
- 从提交回执开始建立一个 30 秒截止时间，随后只使用已有持久回执查询等待目标状态。即使 `resumeHook()` 报错，也只能在同一截止时间内查询是否已落盘，不再另开第二个 30 秒窗口。
- 截止后停止发起新查询并清理等待定时器，仍未确认就返回原有不确定错误。单次不可取消的存储 I/O 结算后不得再启动下一轮；不把逻辑截止时间描述为可中断任意磁盘调用。
- 仅结束当前等待，不取消受理工作流、Session 或业务 Turn，不删除回执。`beginHostRuntimeAcceptance()` 的原有 hook 就绪约束继续保留。

**审查重点：** 返回超时后没有 `Run.returnValue` 留在后台轮询；持久状态才是受理依据，网络错误不写 `NOT_ACCEPTED`。

## R06：新 token 查询不扫描全部历史 hook

补丁落在 world-local 的 `dist/storage/hooks-storage.js`、`dist/storage/hook-index.js`，由现有 `world-local.mjs` 接入；启动准备接入依赖 `dist/index.js` 的 `start()`。

直接复用现有 token claim、token-index、id-index、by-run 索引：

1. `findHookByToken()` 查 claim；缺失时交给现有按 token 的事件索引恢复。删除每次 miss 都枚举全部 `hooks/*.json` 的路径。不缓存“不存在”，避免错过其他进程刚创建的 hook。
2. 启动时先完成现有索引补齐，再扫描一次旧 hook 实体，为仍有效且缺少 claim 的实体补齐现有格式的 claim；完成后才恢复活动运行并就绪。每次进程启动执行一次，进程内复用同一准备 Promise，不新增持久版本标记。直接使用 storage 的入口也必须等待这份准备结果。
3. 补齐使用现有 exclusive-create、保留期和 disposal 检查。不能覆盖其他 owner 的 claim，不能复活已处置或过期 hook；同 token 多个有效 owner 无法唯一确定时报告冲突并停止就绪，不自行选一个。并发写入竞争由现有 claim 机制判定，不能靠内存锁代替。
4. 保留未完成创建时的原生恢复与互斥机制。claim 缺失不直接变成业务 `NOT_ACCEPTED`；底层 HookNotFound 在受理查询中的不确定映射保持不变。
5. 首次部署在服务停止、数据已备份的条件下启动。读取失败或补齐失败不放行就绪；重试可幂等续做。旧实体、回执和事件不删除、不改写，旧版本仍可读取补齐后的数据。

**审查重点：** 新 token 查询的历史实体读取量在准备完成后为零；只允许访问该 token 的记录。100、1000 个历史 hook 下均成立。旧数据丢失 claim、只有实体、带 tag、保留期内终态、disposed、并发创建均有明确结果。启动扫描成本与在线请求成本分开统计。

## R07：受理预算与定位闭环

补充核查已关联出：同一请求 14:21 返回 503，14:25 才持久确认 `ACCEPTED`，随后业务执行完成。此次生产错误的底层 cause 未保留；独立 SDK 探针证实不传 signal 时约 300 秒触发 `UND_ERR_HEADERS_TIMEOUT`。不能据此追认生产那一次一定是相同错误。

**本方案采用一个 Agent 提交等待预算：90 秒上限，与 Apps 当前默认提交预算一致；调用方更早断开则更早结束等待。** 这是本方案的实施取值，不是已有 Agent 行为。创建、续接、补充输入在入口创建一次截止时间，向 Eve SDK 和本次提交内的恢复查询传同一 signal，不逐层重置。独立的请求恢复接口保留已有 30 秒查询约束。详见[Agent 交付](baigong-040-agent-handoff.md)。

eve 在 `public/channels/eve.ts`、`runtime/host-runtime/acceptance.ts`、`execution/workflow-runtime.ts` 的实际受理链记录以下阶段的开始、结束、耗时和结果：鉴权/host runtime 解析、查找或创建受理工作流、受理 hook 就绪、创建 Session、Session command hook 就绪、记录受理回执。继续消息及补充输入记录对应的命令派发阶段。复用现有日志工具，不另建监控系统。

日志关联使用经过校验的 queryId、runId 和 acceptanceKey 摘要；错误只保留受控的 name/code、HTTP 状态和有界 cause 分类。不记录令牌、请求消息、文件内容、任意原始错误文本。Agent 同时保留首次发送失败与恢复失败分类，避免后者掩盖前者。

**超时修复的完成条件：** R02—R06 完成后，用最终制品执行实际受理和延迟受理恢复。若仍有分钟级间隙，根据阶段记录定位到实际等待的队列、存储或 hook 操作，在所属模块修复后复验；该项保持未完成，禁止通过延长预算或仅验证 health=200 结案。现有证据不足以预先指定这段未知阻塞的某一行代码。
